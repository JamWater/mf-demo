## 二、第一维度：核心业务能力增强（生产落地必备）

### 2.1 全局权限体系 + 路由守卫

#### 目标

基座统一管控登录状态与路由权限，子应用无需重复实现权限逻辑，仅做页面内细粒度控制。

#### 实现方案

1. **基座路由守卫**
   在 `host/src/router/guard.tsx` 中实现全局路由拦截，结合全局用户状态校验登录态与权限：

```
import { Navigate, useLocation } from 'react-router-dom';
import { useUserStore } from '../store/useUserStore';

interface Props {
  children: React.ReactNode;
  requiredPermission?: string;
}

export default function RouteGuard({ children, requiredPermission }: Props) {
  const location = useLocation();
  const { token, userInfo } = useUserStore();

  // 未登录拦截
  if (!token) {
    return <Navigate to="/login" state={{ from: location.pathname }} replace />;
  }

  // 权限点校验
  if (requiredPermission && !userInfo?.permissions.includes(requiredPermission)) {
    return <div>无访问权限</div>;
  }

  return <>{children}</>;
}
```

2. **路由配置接入守卫**

```
// host/src/App.tsx
<Routes>
  <Route path="/" element={<Home />} />
  <Route
    path="/user/*"
    element={
      <RouteGuard requiredPermission="user:view">
        <RemoteUserCenter basePath="/user" />
      </RouteGuard>
    }
  />
</Routes>
```

3. **子应用细粒度控制**
   子应用通过共享的 `useUserStore` 获取权限列表，控制按钮、菜单显隐。

#### 收益

- 权限逻辑统一收口，避免多子应用重复开发
- 登录态、权限变更全局同步，无一致性问题

### 2.2 三级错误兜底体系

#### 目标

彻底避免子应用异常导致整个系统白屏，保障生产环境稳定性。

#### 实现方案

1. **一级：子应用加载失败兜底**
   基座侧封装远程组件加载错误边界，加载超时 / 失败时显示降级页面，支持重试：

```
// host/src/components/RemoteErrorBoundary.tsx
import React, { Component } from 'react';

interface State {
  hasError: boolean;
}

export default class RemoteErrorBoundary extends Component<{ children: React.ReactNode }, State> {
  state = { hasError: false };

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  componentDidCatch(error: Error) {
    console.error('子应用加载失败:', error);
  }

  handleRetry = () => {
    this.setState({ hasError: false });
    window.location.reload();
  };

  render() {
    if (this.state.hasError) {
      return (
        <div style={{ padding: 40, textAlign: 'center' }}>
          <h4>服务暂不可用</h4>
          <button onClick={this.handleRetry}>重试</button>
        </div>
      );
    }
    return this.props.children;
  }
}
```

2. **二级：页面级错误边界**
   子应用每个路由页面外层包裹错误边界，单个页面崩溃不影响整个子应用。
3. **三级：全局错误监控上报**
   统一捕获子应用运行时错误，对接监控平台（如 Sentry），实现错误溯源。

### 2.3 统一布局与主题体系

#### 目标

基座提供全局导航、侧边栏、面包屑，子应用仅渲染业务内容区，保证视觉一致性。

#### 实现方案

- 基座实现全局布局组件，包含顶部导航、侧边菜单、内容区插槽
- 主题状态存入全局 store，子应用自动同步
- 子应用无需开发布局组件，专注业务逻辑

## 三、第二维度：架构解耦升级（中大型团队标准）

### 3.1 抽离公共共享包（替代反向依赖）

#### 背景痛点

当前子应用直接 `import 'host/useUserStore'` 属于强反向依赖，子应用无法独立运行、独立打包，耦合度高，团队扩大后维护成本激增。

#### 解决方案

抽离独立 npm 共享包 `@mf/shared`，存放所有通用能力：

- 全局状态类型定义与核心实现
- 通用工具函数
- 基础组件
- 类型声明与协议定义

#### 落地方式

1. 新建独立仓库 / 目录维护共享包，发布到内部 npm 源
2. host 和 remote 同时安装该依赖
3. Module Federation 配置中共享该包为单例，运行时仅加载一份
4. 子应用从共享包导入能力，不再直接导入基座内部模块

#### 收益

- 彻底消除反向依赖，子应用可独立开发、独立部署
- 多子应用复用时一致性最高，版本统一管理
- 符合微前端「高内聚、低耦合」的架构原则

### 3.2 跨应用通信总线（EventBus）

#### 目标

通过发布订阅模式实现跨应用通信，替代直接状态修改的耦合方式。

#### 实现方案

```
// 共享包中实现：@mf/shared/utils/eventBus
type EventCallback = (...args: any[]) => void;

class EventBus {
  private events: Map<string, EventCallback[]> = new Map();

  on(event: string, callback: EventCallback) {
    if (!this.events.has(event)) {
      this.events.set(event, []);
    }
    this.events.get(event)!.push(callback);
  }

  emit(event: string, ...args: any[]) {
    this.events.get(event)?.forEach(cb => cb(...args));
  }

  off(event: string, callback: EventCallback) {
    const callbacks = this.events.get(event);
    if (!callbacks) return;
    this.events.set(event, callbacks.filter(cb => cb !== callback));
  }
}

export const eventBus = new EventBus();
```

#### 典型使用场景

- 子应用通知基座打开全局弹窗、切换侧边栏
- 基座通知子应用刷新数据、切换主题
- 子应用之间互相通知事件

### 3.3 子应用接入协议标准化

#### 目标

定义统一的接入规范，新增子应用无需修改基座代码，按协议接入即可。

#### 标准协议

表格

| 类型       | 约定项        | 说明               |
| ---------- | ------------- | ------------------ |
| 入参 Props | `basePath`    | 基座分配的路由前缀 |
| 入参 Props | `userInfo`    | 全局用户信息       |
| 入参 Props | `permissions` | 用户权限列表       |
| 入参 Props | `eventBus`    | 全局通信总线实例   |
| 暴露方法   | `mount`       | 子应用挂载钩子     |
| 暴露方法   | `unmount`     | 子应用卸载钩子     |

## 四、第三维度：工程化与开发体验优化

### 4.1 远程模块类型自动同步

#### 背景痛点

当前手动维护 `host-typings.d.ts`，源码修改后类型不同步，维护成本高，容易引发类型 bug。

#### 解决方案

接入 `@module-federation/typescript` 插件：

1. 子应用构建时自动生成类型声明文件
2. 基座开发时自动拉取最新类型
3. 导入远程模块时有完整的智能提示与类型校验

#### 配置方式

在 Rsbuild 配置中接入插件，开启 `dts` 选项即可自动生成类型。

### 4.2 样式隔离方案

#### 方案对比

表格

| 方案         | 隔离程度 | 改造成本 | 适用场景                 |
| ------------ | -------- | -------- | ------------------------ |
| 命名前缀约定 | 弱       | 低       | 小型项目、团队规范度高   |
| CSS Modules  | 中       | 中       | 大部分业务项目           |
| CSS-in-JS    | 强       | 中高     | 组件库、对隔离要求高     |
| Shadow DOM   | 极强     | 高       | 嵌入第三方应用、完全隔离 |

#### 推荐方案

业务项目优先使用 **CSS Modules**，Rsbuild 内置支持，文件名命名为 `xxx.module.scss` 即可自动启用。

### 4.3 性能优化体系

1. **远程模块预加载**
   导航 hover 时预加载子应用 `remoteEntry.js`，点击后秒开。
2. **依赖共享优化**
   仅共享通用第三方库，不共享业务代码，平衡耦合度与体积优化。
3. **子应用路由懒加载**
   子应用内部页面按路由拆分懒加载，降低首屏加载体积。

### 4.4 本地开发联调优化

- 支持灵活切换：本地仅启动当前开发的子应用，其余走测试 / 线上环境
- 统一代理配置，处理接口跨域与环境切换
- 环境变量标准化，多环境一键切换

## 五、第四维度：微前端高级特性

### 5.1 多子应用统一管理

新增订单中心、管理后台等多个业务子应用，基座统一负责：

- 路由分发与权限管控
- 全局布局与主题复用
- 统一的监控与埋点体系

适合多业务域、多团队并行开发的大型系统。

### 5.2 运行时动态注册子应用

#### 能力

子应用配置从后端接口动态拉取，基座根据菜单配置自动注册路由、加载远程模块。

#### 价值

- 无需修改代码、发版即可新增 / 下线子应用
- 支持低代码平台、动态化配置的中后台系统
- 运维灵活性极高

### 5.3 子应用生命周期精细化管控

完善全生命周期钩子：

- `bootstrap`：应用初始化，执行一次性全局逻辑
- `mount`：组件挂载，渲染页面
- `unmount`：组件卸载，清理定时器、事件监听
- `destroy`：完全销毁，释放内存与缓存

核心价值：避免内存泄漏，保障生产环境长期运行稳定性。

### 5.4 子应用保活（Keep-Alive）

切换子应用时不销毁实例，切回时直接恢复状态，保留表单填写、列表滚动位置等用户操作状态，大幅提升体验。

### 5.5 多技术栈兼容

支持 Vue、React 等不同技术栈的子应用接入同一基座，兼容历史项目，无需强制统一技术栈即可整合到同一系统。

## 六、落地优先级与最佳实践

### 6.1 落地顺序（投入产出比从高到低）

1. **第一阶段（生产必备）**：三级错误兜底 + 全局权限体系
2. **第二阶段（架构规范）**：抽离公共共享包 + EventBus 通信总线
3. **第三阶段（效率提升）**：类型自动同步 + 样式隔离 + 性能优化
4. **第四阶段（按需扩展）**：多子应用管理、动态注册、保活等高级特性

### 6.2 核心最佳实践

1. **共享原则**：只共享基础第三方库与通用协议，不共享业务代码，共享越多耦合越高
2. **解耦原则**：子应用优先通过 Props 和 EventBus 与基座通信，避免反向依赖
3. **独立运行原则**：子应用必须能独立启动、独立开发、独立部署
4. **一致性原则**：全局状态、权限、主题由基座唯一管控，避免多份数据源

## 七、常见问题排查

### 7.1 远程模块找不到

- 检查启动顺序：必须先启动被消费的应用，再启动消费方
- 核对 `remotes` 配置中的地址、端口、应用名是否正确
- 确认 `exposes` 配置中的文件路径真实存在

### 7.2 类型声明不生效

- 确认 `.d.ts` 文件在 `src` 目录下，后缀正确
- 确认 `tsconfig.json` 的 `include` 包含声明文件，且未配置 `typeRoots`
- 修改声明文件后重启 TS 服务或 dev server

### 7.3 状态不同步

- 确认共享依赖开启了 `singleton: true`
- 两端依赖大版本必须一致，否则单例会静默失效
- 基座端开启 `eager: true`，子应用端不要开启

### 7.4 Rsbuild 配置不生效

- 在 `package.json` 中添加 `"type": "module"`
- 修改配置后必须完整重启 dev server
- 确认配置文件名严格为 `rsbuild.config.ts`
